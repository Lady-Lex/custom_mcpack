# 🧱 custom_mcpack

## 📌 Project Overview

This repository is used to manage **multiple custom Minecraft modpacks**.  
Each modpack instance (usually a **Minecraft version + mod loader + configuration variant**) is maintained as an **independent directory**, for example:

```
packs/1.21.1-neoforge-v1/
packs/1.20.1-fabric-v2/
```

Each directory represents a modpack definition that is **reproducible, migratable, and maintainable long-term**.

Unlike the traditional approach of “only keeping local JAR files”, this repo is **metadata-first** and uses `packwiz` to declaratively manage mods, enabling more reliable version control and upgrade workflows.

---

## 🎯 Goals & Motivation

This repository structure is mainly designed to solve these long-term maintenance issues:

- 🔄 **Easier Minecraft / loader upgrades**  
  The same mod set can be migrated to a new version quickly based on metadata, without manually re-selecting and re-adding everything.

- ♻️ **Less repeated work**  
  Mod definitions can be reused across multiple modpack instances, avoiding repeated comparisons of JAR files.

- 🧪 **Reproducibility & auditability**  
  Each mod’s source, version, and hash are explicitly recorded, so the pack can be rebuilt at any time.

- 🛠️ **An engineering-style workflow**  
  Manage modpacks like dependency management, not a one-off manual merge.

---

## 🗂️ Modpack Folder Structure

Each modpack directory uses **`packwiz` as the single metadata management tool**. A typical layout:

```
pack.toml
index.toml
mods/
  ├── example-mod.pw.toml
  └── another-mod.pw.toml
docs/
  └── unaddable-mods.txt
```

📄 File notes:

- **`pack.toml`**  
  Base modpack info (Minecraft version, loader type, name, etc.)

- **`index.toml`**  
  File index generated by packwiz

- **`mods/*.pw.toml`**  
  Metadata definition for each mod (source, version, hashes, etc.)

- **`docs/unaddable-mods.txt`**  
  Records of mods that cannot be managed via packwiz

---

## 🚫 Mods That Can’t Be Added Directly (Unaddable Mods)

Some mods **can’t be managed directly via packwiz** for reasons such as:

- ⛔ Requires manual download
- 📜 License / redistribution restrictions
- 📦 Uses an external installer
- ⚠️ Non-standard distribution format

Conventions:

- **Repository root**  
  `UNADDABLE-MODS-TEMPLATE.md`  
  A unified template describing how to record “unaddable mods”

- **Each modpack instance**  
  Only maintains its own concrete record file, for example:

  ```
  packs/1.21.1-neoforge-v1/docs/unaddable-mods.txt
  ```

This mechanism ensures that **exceptions are explicitly documented instead of silently ignored**.

## 🧰 Toolchain

### 📦 packwiz (metadata management)

This repo uses **packwiz** as the core tool for managing mod metadata:

- 🔗 Project  
  https://github.com/packwiz/packwiz

Please follow the official instructions in the packwiz repo to install it.  
After installation, packwiz is mainly used to:

- Initialize modpacks
- Add / update / remove mods
- Maintain `pack.toml`, `index.toml`, and `*.pw.toml`

> ⚠️ **Important**  
> In this repo, `packwiz` is the Single Source of Truth.  
> Managing mods by manually adding/removing JAR files is not recommended.

---

### ⬇️ packwiz-install (download mod JAR files)

`packwiz` only manages **metadata** and does not download mod JAR files directly.  
For actually downloading and deploying mod files, use:

- 🔗 Project  
  https://github.com/ookkoouu/packwiz-install

Recommended workflow:

1. Use `packwiz` to manage and update mod metadata  
2. Use `packwiz-install` to download the corresponding mod JAR files based on that metadata

This workflow clearly separates:

- 🧾 **Definition (Metadata)**
- 📦 **Physical files (JAR Materialization)**

## 🧠 Metadata Helper Script

### `packwiz_to_metadata.py`

This repository includes a helper script to **generate higher-level mod description info from packwiz metadata**, to assist organization and archiving.

### 🔍 What it does

The script will:

- Analyze `mods/*.pw.toml`
- Detect the source (Modrinth / CurseForge)
- When available, call the corresponding API to fetch:
  - 🏷️ Categories / tags
  - 🖥️ Client / server side applicability

It outputs a **“suggested” YAML file** for further manual curation.

---

### ▶️ Usage

#### 📴 Offline mode (no network)

```
python packwiz_to_metadata.py --repo packs/1.21.1-neoforge-v1 --offline
```

#### 🌐 Online mode

Default behavior:

- Modrinth API: no key required
- CurseForge API: key required

You can provide the CurseForge API key in one of these ways:

- **Method 1: environment variable (recommended)**

```
CURSEFORGE_API_KEY=<your_API_key>
```

- **Method 2: CLI argument**

```
python packwiz_to_metadata.py --repo packs/1.21.1-neoforge-v1 --curseforge-api-key <key>
```

---

### 📤 Output file

Default output path:

```
<repo>/mod-metadata.generated.yml
```

Example:

```
packs/1.21.1-neoforge-v1/mod-metadata.generated.yml
```

This is an **auto-generated** file and should be treated as reference input. Review it manually and then merge into the official `mod-metadata.yml`.

---

## 📝 Notes

- The script was originally named `modrinth_to_metadata.py`  
  It has been renamed to **`packwiz_to_metadata.py`** to reflect multi-source support.
- Auto-generated metadata should not be treated as the final source of truth.
